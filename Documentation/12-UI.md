# 12 — UI: The Hub, Every Panel, and the Skill Tree Node-Graph Editor

## Overview

The largest folder in the project (38 files) but not, in practice, the most conceptually complex — most of its size comes from **reuse paying off**: a handful of shared base classes (`UI_ItemSlot`, `UI_ItemSlotParent`/`UI_EquipSlotParent`, `UI_ToolTip`) get extended or reused across Character, Craft, Merchant, Storage, and Quest panels, so once you understand the base, most of what follows is "the same idea, one new click behavior." This doc covers `UI.cs` (the hub) and each sub-panel folder in full, but leans on that reuse rather than re-explaining the same shared logic every time it appears.

Two structural notes worth having up front.

First: throughout this folder you'll see **public, parameterless methods with no C# callers anywhere** (`UI_MainMenu.PlayGame()`, `UI_Options.MainMenu()`, `UI_CraftPreview.ConfirmCraft()`, `UI_QuestPreview.AcceptQuestBTN()`, and others). These aren't dead code — they're wired up as **Unity UI Button `OnClick()` handlers** directly in the Inspector, a third "invisible to a code search" wiring mechanism alongside the Animation Event bridge (`02-Entity.md`) and skill-tree node clicks. Worth recognizing the pattern on sight rather than wondering why a public method has no callers.

Second: UI click handling here uses Unity's **`IPointerDownHandler`/`IPointerEnterHandler`/`IPointerExitHandler`** interfaces — a third distinct input-reading style in this project, alongside the new Input System (`03-Player.md`) for gameplay and occasional direct `Input.GetKey` calls for a few UI modifier checks (see below). This isn't inconsistency — Unity's EventSystem-routed pointer interfaces are the standard, idiomatic way to handle clicks on UI elements specifically, a different concern from gameplay input entirely.

## Part 1 — `UI.cs`: the hub and the exclusive-panel system

```csharp
public class UI : MonoBehaviour
{
    public static UI Instance;
    [SerializeField] private GameObject[] uiElements;
    public bool alternativeInput { get; private set; }
    private PlayerInputSet input;

    public UI_SkillToolTip skillToolTip { get; private set; }
    public UI_ItemToolTip itemToolTip { get; private set; }
    // ... one property per sub-panel
```
`Instance` here is a plain `public static UI Instance;` field — not even a `{ get; private set; }` property, the loosest form of the unguarded-singleton pattern seen throughout this project (`Concepts-Glossary`).

### Finding every sub-panel, including the ones that start hidden

```csharp
private void Awake()
{
    Instance = this;
    skillToolTip = GetComponentInChildren<UI_SkillToolTip>();
    ...
    skillTreeUI = GetComponentInChildren<UI_SkillTree>(true); // This line is can find skill tree if it is inactive
    inventoryUI = GetComponentInChildren<UI_Inventory>(true);
    // ...one GetComponentInChildren(true) per major panel
}
```
The `true` argument (`include inactive`) matters a great deal here, and the source's own inline comments say exactly why: most of these panels start `SetActive(false)` (closed) by default, so without `true`, every one of these lookups would silently return `null` for any panel that isn't currently open. This is the hub-pattern idea (`03-Player.md`'s `Player.cs`) applied to UI — every sub-panel gets resolved once here, and every other script reaches it through `ui.someUI` instead of its own scene search.

### The exclusive-panel mechanism — CLAUDE.md's description, made concrete

```csharp
private void SwitchTo(GameObject objectToSwitchOn)
{
    foreach (var element in uiElements)
        element.gameObject.SetActive(false);
    objectToSwitchOn.SetActive(true);
}
```
This one method is the literal implementation of CLAUDE.md's "enforces exclusive panel open/close" — `uiElements` is a flat array of top-level panel GameObjects (assigned in the Inspector), and `SwitchTo` always disables every single one before enabling the target. `OpenOptionsUI`/`CloseOptionsUI`/`SwitchToInGameUI` all funnel through this.

### Disabling player input while any panel is open

```csharp
private void StopPlayerControlsIfNeeded()
{
    foreach (var element in uiElements)
        if (element.activeSelf) { StopPlayerControls(true); return; }
    StopPlayerControls(false);
}
```
This is the other half of CLAUDE.md's description — checking "is *any* panel currently open" and disabling `input.Player` (the gameplay action map, `03-Player.md`) accordingly, called from `ToggleSkillTreeUI`/`ToggleInventoryUI`. Notice `ToggleSkillTreeUI` and `ToggleInventoryUI` are near-identical five-line methods (`SetAsLastSibling` for render order, hide tooltips, toggle active, stop controls if needed) that could have been one shared helper parameterized by which panel — a small, genuine duplication worth recognizing alongside similar ones already flagged in earlier chapters (`Object_Merchant`/`Object_Blacksmith`'s `EnsurePlayerInventory` in `10-InteractiveObjects.md`).

### A real, three-times-confirmed inconsistency: `alternativeInput` is set up but never read

```csharp
input.UI.AlternativeInput.performed += ctx => alternativeInput = true;
input.UI.AlternativeInput.canceled += ctx => alternativeInput = false;
```
`UI.cs` wires this bool up properly through the new Input System. But **every place in this folder that actually needs a "hold a modifier key for the full-stack variant of an action" check bypasses it entirely**:

- `UI_ItemSlot.OnPointerDown` — `bool alternativeInput = Input.GetKey(KeyCode.LeftControl);`
- `UI_MerchantSlot.OnPointerDown` — `Input.GetKey(KeyCode.LeftControl)` for both buy and sell
- `UI_StorageSlot.OnPointerDown` — same, for transfers

All three independently hardcode the **old** `Input` class and `KeyCode.LeftControl` directly, never referencing `ui.alternativeInput` at all. Having seen this exact same substitution three separate times across three unrelated files is enough to call it a real, confirmed pattern rather than a one-off: `UI.alternativeInput` appears to be unused dead wiring, with every actual consumer independently reinventing the same check a different way.

### Opening/closing each panel — mostly one template, one real exception

```csharp
public void OpenStorageUI(bool openStorageUI)
{
    storageUI.gameObject.SetActive(openStorageUI);
    StopPlayerControls(openStorageUI);
    if (!openStorageUI) { craftUI.gameObject.SetActive(false); HideToolTips(); }
}
```
Most `OpenXUI` methods follow this shape: toggle the panel, toggle player controls to match, and on close, hide tooltips (`OpenMerchantUI` is nearly identical; `OpenStorageUI` additionally closes the Craft panel alongside Storage, since Craft is always opened *from* Storage).

`OpenDeathScreenUI` is the deliberate exception:
```csharp
public void OpenDeathScreenUI()
{
    // HideToolTips();
    // StopPlayerControls(true);
    SwitchTo(deathScreenUI.gameObject);
    input.Disable(); // Pay attention to this line if we import gamepad
}
```
It skips the usual tooltip/controls calls (commented out, not deleted) and instead disables the **entire** input object — not just the `Player` action map, everything, including UI navigation — worth quoting the developer's own forward-looking note directly: `// Pay attention to this line if we import gamepad`. A genuinely useful flag for future-you (or anyone extending this project) that gamepad UI navigation would need to revisit exactly this line.

## Part 2 — Root-level screens

### `UI_FadeScreen.cs` — the coroutine `GameManager` waits on

```csharp
public Coroutine fadeEffectCo { get; private set; }

private void FadeEffect(float targetAlpha, float duration)
{
    if (fadeEffectCo != null) StopCoroutine(fadeEffectCo);
    fadeEffectCo = StartCoroutine(FadeEffectCo(targetAlpha, duration));
}

private IEnumerator FadeEffectCo(float targetAlpha, float duration)
{
    float startAlpha = fadeImage.color.a;
    float elapsedTime = 0f;
    while (elapsedTime < duration)
    {
        elapsedTime += Time.deltaTime;
        var color = fadeImage.color;
        color.a = Mathf.Lerp(startAlpha, targetAlpha, elapsedTime / duration);
        fadeImage.color = color;
        yield return null;
    }
}
```
This is the concrete implementation behind `yield return fadeScreenUI?.fadeEffectCo;` from `05-GameManager-and-Scenes.md`'s `ChangeSceneCo` walkthrough — `fadeEffectCo`, exposed as a public read-only property, is exactly the `Coroutine` object `GameManager` yields on to wait for the fade to finish. `FadeIn`/`FadeOut` are mirror-image public entry points (transparent↔black), both funneling through the same `FadeEffect`/`FadeEffectCo` pair, which restarts cleanly (`StopCoroutine` first) if a new fade is requested mid-fade.

### `UI_MainMenu.cs`, `UI_Options.cs`, `UI_DeathScreen.cs` — button-hookup scripts

All three are collections of small public methods meant to be wired to Button `OnClick()` events in the Inspector (see the Overview's note on this pattern) — `UI_MainMenu.PlayGame()` plays a click SFX then calls `GameManager.Instance.ContinuePlay()` (`05-GameManager-and-Scenes.md`); `UI_DeathScreen.GoToTown()`/`LastCheckpoint()`/`MainMenu()` call `GameManager.Instance.ChangeScene(...)`/`RestartScene()` directly. Worth noting `UI_MainMenu.Start()` reaches for `UI_Options`/`UI_FadeScreen` via `transform.root.GetComponentInChildren<...>()` rather than going through the `UI` hub — a direct scene-tree search instead, plausibly because the Main Menu scene's UI setup was built independently of the in-game `UI` hub pattern.

### `UI_Options.cs` — a second, separate persistence system, and why the sliders use `Log10`

```csharp
private void OnEnable()
{
    sfxVolumeSlider.value = PlayerPrefs.GetFloat(sfxParameter, .6f);
    bgmVolumeSlider.value = PlayerPrefs.GetFloat(bgmParameter, .6f);
}
private void OnDisable()
{
    PlayerPrefs.SetFloat(sfxParameter, sfxVolumeSlider.value);
    PlayerPrefs.SetFloat(bgmParameter, bgmVolumeSlider.value);
}
```
Worth flagging clearly: audio volume is **not** part of the `GameData`/`SaveManager` JSON save file covered in `09-SaveSystem.md` at all — it uses Unity's built-in `PlayerPrefs`, a separate, simpler OS-level key-value store. A reasonable, deliberate choice: volume is a device/user preference, not game progress, so keeping it independent means it persists the same way regardless of which save file is loaded.

```csharp
public void BGMSliderValue(float value)
{
    float newValue = Mathf.Log10(value) * mixerMultiplier;
    audioMixer.SetFloat(bgmParameter, newValue);
}
```
Worth explaining *why* this conversion exists rather than feeding the slider's `0`–`1` value straight to the mixer: human hearing perceives loudness **logarithmically**, not linearly, and Unity's `AudioMixer` volume parameters are expressed in decibels (an inherently logarithmic scale). Feeding a linear `0`–`1` slider value directly as decibels would make most of the audible volume change happen in a tiny sliver of the slider's range. Converting through `Mathf.Log10` first is what makes a linear slider *feel* linear to the ear — genuine, real applied audio engineering, not an arbitrary formula.

## Part 3 — The `UI_ItemSlot` family: one base, seven click behaviors

This is the single best example of inheritance-for-reuse in the whole UI folder — worth understanding thoroughly once, since six other classes build directly on it.

```csharp
public class UI_ItemSlot : MonoBehaviour, IPointerDownHandler, IPointerEnterHandler, IPointerExitHandler
{
    public Inventory_Item itemInSlot { get; private set; }
    protected Inventory_Player inventory;
    protected UI ui;
    protected RectTransform rect;

    public virtual void OnPointerDown(PointerEventData eventData)
    {
        if (itemInSlot == null || itemInSlot.itemData.itemType == ItemType.Material) return;
        bool alternativeInput = Input.GetKey(KeyCode.LeftControl);
        if (alternativeInput) inventory.RemoveOneItem(itemInSlot);
        else if (itemInSlot.itemData.itemType == ItemType.Consumable) inventory.TryUseItem(itemInSlot);
        else inventory.TryEquipItem(itemInSlot);
    }

    public void UpdateSlot(Inventory_Item item)
    {
        itemInSlot = item;
        if (itemInSlot == null) { itemStackSize.text = ""; itemIcon.color = Color.clear; return; }
        itemIcon.color = new Color(1, 1, 1, .9f);
        itemIcon.sprite = itemInSlot.itemData.itemIcon;
        itemStackSize.text = itemInSlot.stackSize > 1 ? itemInSlot.stackSize.ToString() : "";
    }
}
```
`UpdateSlot(item)` is the shared "paint this slot's visuals from an `Inventory_Item`" method — every subclass below reuses it **unchanged**. The base `OnPointerDown` is the general-inventory click behavior: Ctrl+click quick-removes one, otherwise a `Consumable` uses itself (`Inventory_Base.TryUseItem`, `07-InventorySystem.md`) and anything else tries to equip (`Inventory_Player.TryEquipItem`).

Six subclasses each `override OnPointerDown` (and sometimes `OnPointerEnter`) to redirect the click to a *different* inventory operation, while keeping `UpdateSlot`'s visuals for free:

| Subclass | What clicking does instead |
|---|---|
| `UI_EquipmentSlot` | `inventory.UnequipItemFromSlot(itemInSlot)` — an item already equipped comes off on click, mirroring the base class equipping it from the general inventory |
| `UI_QuickItemSlot` | Opens a popup of consumable choices (`ui.inGameUI.OpenQuickItemOptions`) rather than using the item directly |
| `UI_QuickItemSlotOption` | Assigns whichever item this option represents to the quick slot that opened the popup, then closes it |
| `UI_MerchantSlot` | Branches on left/right mouse button **and** a `MerchantSlotType` enum — buy, sell, or fall through to the base equip/use behavior (below) |
| `UI_StorageSlot` | Branches on a `StorageSlotType` enum — transfer player→storage or storage→player |
| `UI_QuestRewardSlot` | **Does nothing** (`{ }`) — an intentionally empty override |

### `UI_EquipmentSlot` — opposite operations from the same click gesture

```csharp
public override void OnPointerDown(PointerEventData eventData)
{
    if (itemInSlot == null) return;
    inventory.UnequipItemFromSlot(itemInSlot);
}
```
A tidy piece of UI design worth noticing: clicking an item in the *general* inventory equips it (base class behavior); clicking that same item once it's shown in an *equipment* slot unequips it — the same click gesture does the logically opposite thing depending purely on which slot type it landed in, which reads naturally to a player without needing separate buttons.

### `UI_QuickItemSlot` — simulating a button press for keyboard-triggered feedback

```csharp
public void SimulateButtonFeedback()
{
    EventSystem.current.SetSelectedGameObject(button.gameObject);
    ExecuteEvents.Execute(button.gameObject, new BaseEventData(EventSystem.current), ExecuteEvents.submitHandler);
}
```
Called from `UI_InGame.PlayQuickSlotFeedback` (below), itself wired to `Inventory_Player.OnQuickSlotUsed` (`07-InventorySystem.md`) — which fires when a quick item is used via the **keyboard shortcut** (`Player.OnEnable`'s `QuickItemSlot_1`/`QuickItemSlot_2` bindings, `03-Player.md`), not a mouse click. Since no real click ever happened, there's nothing to trigger the button's normal visual press feedback — this method manufactures one programmatically through Unity's `EventSystem`, so the UI still visibly reacts to a keyboard-triggered item use exactly as if it had been clicked.

### `UI_QuestRewardSlot` — an intentionally empty override, and why

```csharp
public override void OnPointerDown(PointerEventData eventData) { }
public override void OnPointerEnter(PointerEventData eventData)
{
    if (itemInSlot == null) return;
    ui.itemToolTip.ShowToolTip(true, rect, itemInSlot, false, false, false);
}
```
A quest's previewed reward isn't something you own yet — clicking it to equip/use/remove it wouldn't make sense. Rather than not inheriting `UI_ItemSlot` at all, overriding `OnPointerDown` with an empty body keeps the free `UpdateSlot` visuals **and** the tooltip-on-hover behavior (still wanted, just with extra flags telling the tooltip to hide quantity/purchase controls), while cleanly disabling only the one piece of behavior that doesn't apply here.

## Part 4 — Character UI

- **`UI_Inventory`** (panel) — subscribes to `Inventory_Player.OnInventoryChanged` (`07-InventorySystem.md`), refreshes the general item grid and equipment slots and the gold display.
- **`UI_ItemSlotParent`** / **`UI_EquipSlotParent`** — the generic "grid of slots" updaters, worth understanding as **shared infrastructure reused across five different panels**: `UI_ItemSlotParent` (finds its `UI_ItemSlot` children once, lazily, then pushes list items into them by index, clearing any leftover slots past the list's length) is reused by `UI_Inventory`, `UI_Craft`, `UI_Merchant`, `UI_Storage`, and `UI_Quest`; `UI_EquipSlotParent` (the same idea for equipment slots) is reused by `UI_Inventory` and `UI_Merchant`. This pair is doing a lot of quiet, uncredited work across the whole UI folder.
- **`UI_PlayerStats`** — loops every child `UI_StatSlot` calling `UpdateStatValue()` whenever `OnInventoryChanged` fires (since equipping/unequipping gear changes stats).
- **`UI_StatSlot`** — the character-sheet display, and worth a direct, honest callout: its `GetStatType(StatType)` and `IsPercentageStat(StatType)` methods are **near-verbatim duplicates** of the exact same two methods already documented on `Inventory_Item.GetItemInfo` (`07-InventorySystem.md`) — the same lookup logic, copy-pasted into a second unrelated class rather than shared through one utility. `UpdateStatValue()`'s own large `switch` is worth distinguishing from `Entity_Stats.GetStatByType` (`02-Entity.md`): that method returns the raw, editable `Stat` object (for buffs/equipment to modify); this one wants the **final displayed number** — for stats with bonus formulas layered on top (crit chance, armor, evasion...), it calls the specific `Get*()` calculation method directly (`playerStats.GetCritChance()`, `GetArmorReduction() * 100`, etc.) rather than reading the raw `Stat`, since that's what should actually be shown to the player.

        healthRect.sizeDelta = new Vector2(maxHealth * .2f, healthRect.sizeDelta.y);

Worth a small callout: the health bar's pixel **width**, not just its fill amount, scales directly with the max-health stat (`maxHealth * .2f`) — a character with more max health gets a visibly wider bar, not just a same-size bar with a different fill percentage.

### `UI_MiniHealthBar` — the payoff of `Entity.onFlipped`

```csharp
private void OnEnable() { if (entity != null) entity.onFlipped += HandleFlip; }
void HandleFlip() => transform.rotation = Quaternion.identity;

// void Update()
// {
//     //Quite heavy load on the FPS, does it all the time even if not required
//     transform.rotation = Quaternion.identity;
// }
```
This closes a loop `02-Entity.md` left open — `Entity.onFlipped` was documented as an event with no concrete consumer shown yet; this is that consumer. Recall `Entity.Flip()` rotates the **whole Transform** 180° (`02-Entity.md`) — if a floating health bar is a child of that transform, it would visually flip upside-down along with everything else unless something corrects it. `HandleFlip()` snaps the bar's own rotation back to `Quaternion.identity` every time the parent flips, keeping player-readable UI right-side-up regardless of which way the character faces.

The commented-out `Update()` is genuinely valuable to read directly: it's the **previous** implementation — correcting rotation unconditionally, every single frame, regardless of whether a flip ever happened — replaced by the event-driven version above specifically for performance (per the developer's own comment). This is a clean, real example of *why* event-driven correction beats per-frame polling: the fix only runs exactly when it's needed, not 60+ times a second "just in case."

## Part 7 — Merchant UI and Storage UI (near-identical structure)

Both panels follow the same shape: subscribe to the relevant inventory's `OnInventoryChanged`, refresh two or three `UI_ItemSlotParent`/`UI_EquipSlotParent` groups, update a gold display. Their slot classes both extend `UI_ItemSlot` and both branch on a small local enum to decide which direction a click should move an item:

```csharp
// UI_MerchantSlot
public enum MerchantSlotType { MerchantSlot, PlayerSlot }
if (slotType == MerchantSlotType.PlayerSlot)
{
    if (rightButton) merchant.TrySellItem(itemInSlot, sellFullStack);
    else if (leftButton) base.OnPointerDown(eventData); // normal equip/use
}
else if (slotType == MerchantSlotType.MerchantSlot && !leftButton)
    merchant.TryBuyItem(itemInSlot, buyFullStack);
```
```csharp
// UI_StorageSlot
public enum StorageSlotType { StorageSlot, PlayerInventorySlot }
if (slotType == StorageSlotType.StorageSlot) storage.FromStorageToPlayer(itemInSlot, transferFullStack);
if (slotType == StorageSlotType.PlayerInventorySlot) storage.FromPlayerToStorage(itemInSlot, transferFullStack);
```
The same slot class handles two different roles ("this is the shop's stock" vs. "this is your own inventory, shown inside the shop's UI") purely by which enum value is set on each individual slot in the Inspector — one script, reused for both halves of the same panel. Both call `Inventory_Merchant.TryBuyItem`/`TrySellItem` and `Inventory_Storage.FromStorageToPlayer`/`FromPlayerToStorage` directly from `07-InventorySystem.md`, and both use the same old-`Input.GetKey(KeyCode.LeftControl)` pattern already flagged in Part 1 — a third confirmed instance.

## Part 9 — Skill Tree UI: the node-graph editor

CLAUDE.md singles this out as "a fully custom node-graph editor... one of the more original subsystems, not a third-party asset" — worth giving it the depth that description promises.

### `UI_SkillTree` — points, save data, and two kinds of "unlocked"

```csharp
public bool EnoughSkillPoints(int cost) => skillPoints >= cost;
public void RemoveSkillPoints(int cost) { skillPoints -= cost; UpdateSkillPointsText(); }
public void AddSkillPoints(int amount) { skillPoints += amount; UpdateSkillPointsText(); }
```
The currency every node spends from — `AddSkillPoints` is exactly what `ItemEffect_GrantSkillPoint` (`11-Data-ScriptableObjects.md`) calls.

```csharp
[ContextMenu("Reset Skill Tree")]
public void ResetSkillTree()
{
    foreach (var node in GetComponentsInChildren<UI_TreeNode>()) node.Refund();
}
```
Exactly what `ItemEffect_RefundAllSkills` (`11-Data-ScriptableObjects.md`) calls through `ui.skillTreeUI.ResetSkillTree()`.

```csharp
public void SaveData(ref GameData data)
{
    data.skillPoints = skillPoints;
    data.skillTreeUI.Clear();
    data.skillUpgrades.Clear();
    foreach (var node in allTreeNodes)
        data.skillTreeUI[node.skillData.displayName] = node.isUnlocked;
    foreach (var skill in skillManager.allSkills)
        data.skillUpgrades[skill.GetSkillType()] = skill.GetUpgradeType();
}
```
This is worth explaining carefully, because it reveals a genuinely important distinction the save data has to preserve: **"unlocked" and "equipped" are not the same thing.**

- `skillTreeUI` (keyed by node display name — worth a light flag that this uses the node's *display name string* as its save key, rather than a more robust dedicated ID, a real fragility if two nodes ever shared a name) records which individual nodes the player has permanently spent points on and unlocked.
- `skillUpgrades` separately records which single `SkillUpgradeType` is *actively equipped* per skill.

These can genuinely differ: a player can unlock tier-1 *and* tier-2 of the same mutually-exclusive branch (both remain `isUnlocked = true` forever, since nothing in `UI_TreeNode.Unlock()` re-locks an earlier node in the same chain), while only the *most recently unlocked* one is the live `upgradeType` actually running on the `Skill_Base` component (`08-SkillSystem.md` established that `SetSkillUpgrade` **overwrites** the previous upgrade) — so the save file has to track both independently to correctly restore "which nodes show as unlocked in the tree" and "which one is actually active" on load.

`UnlockDefaultSkills()` (called once from `UI.Start()`) is worth noting as running **alongside**, not instead of, `Skill_Base.Start()`'s own `unlockedByDefault` check (`08-SkillSystem.md`) — both independently key off the same `Skill_DataSO.unlockedByDefault` flag, because each serves a genuinely different job: `Skill_Base` needs its own live `upgradeType`/`cooldown` set correctly (gameplay state), while `UI_TreeNode` needs to visually render as unlocked (UI display state) — two halves of the same starting condition, applied through two separate code paths rather than one calling the other.

### `UI_TreeNode` — prerequisites, conflicts, and a cascading lock-out

```csharp
public UI_TreeNode[] neededNodes;
public UI_TreeNode[] conflictNodes;
public bool isUnlocked;
public bool isLocked;
```
Two genuinely distinct bools worth being crisp about: `isUnlocked` means "the player has spent points here"; `isLocked` means "this node has been permanently ruled out because a *conflicting* node elsewhere was chosen instead" — conflating them would be an easy mistake.

```csharp
private bool CanBeUnlocked()
{
    if (isLocked || isUnlocked) return false;
    if (!skillTree.EnoughSkillPoints(skillData.cost)) return false;
    foreach (var node in neededNodes) if (!node.isUnlocked) return false;
    foreach (var node in conflictNodes) if (node.isUnlocked) return false;
    return true;
}
```
The full gate: not already locked or unlocked, affordable, every prerequisite node already unlocked, and none of the conflicting nodes already chosen.

```csharp
private void Unlock()
{
    if (isUnlocked) return;
    isUnlocked = true;
    UpdateIconColor(Color.white);
    LockConflictNodes();
    skillTree.RemoveSkillPoints(skillData.cost);
    connectHandler.UnlockConnectionImage(true);
    skillTree.skillManager.GetSkillByType(skillData.skillType).SetSkillUpgrade(skillData);
}

private void LockConflictNodes()
{
    foreach (var node in conflictNodes) { node.isLocked = true; node.LockChildNodes(); }
}
public void LockChildNodes()
{
    isLocked = true;
    foreach (var node in connectHandler.GetChildNodes()) node.LockChildNodes();
}
```
The last line of `Unlock()` is the actual gameplay payoff, shown from the trigger side this time — `08-SkillSystem.md` covered what `SetSkillUpgrade` *does*; this is *where* it's called from when a player clicks a node. `LockConflictNodes`/`LockChildNodes` is worth tracing carefully: choosing this node doesn't just lock out its immediate conflicting node — it **recursively cascades** the lock down through every one of *that* node's own children too (`LockChildNodes` calling itself on each child returned by `connectHandler.GetChildNodes()`). This is the mechanism that makes "commit to one branch, permanently lose the *entire rest* of the conflicting branch" actually work, not just the one directly-conflicting node.

### `UI_TreeConnectHandler`/`UI_TreeConnection` — programmatically computed layout

This is the part worth genuine appreciation as custom tooling, given CLAUDE.md's note that the project has **no** `Assets/Editor/` folder at all.

```csharp
public void UpdateConnection()
{
    for (int i = 0; i < connectionDetails.Length; i++)
    {
        var detail = connectionDetails[i];
        var connection = connections[i];
        Vector2 targetPosition = connection.GetConnectionPoint(myRectTransform);
        connections[i].DirectConnection(detail.direction, detail.length, detail.rotation);
        if (detail.childNode == null) continue;
        detail.childNode.SetPosition(targetPosition);
        detail.childNode.SetConnectionImage(connection.GetConnectionImage());
    }
}
```
Worth stating plainly what this means: **child node positions in the skill tree are not manually placed by hand in the Editor.** Each `UI_TreeConnectDetails` entry configures a *direction* (a compass-style `NodeDirectionType` enum — Up, UpRight, Right, DownRight...), a *length*, and a fine-tuning *rotation offset*; `UI_TreeConnection.DirectConnection` converts that direction into an actual rotation angle (`GetDirectionAngle`'s switch — `UpRight` → 45°, `Right` → 0°, and so on) and stretches a connector-line image to the configured length; then `GetConnectionPoint` — using `RectTransformUtility.ScreenPointToLocalPointInRectangle`, a Unity UI utility for converting a screen-space point into a RectTransform's own local anchored coordinate space — computes exactly where that line's far end lands, and the child node is **snapped to sit exactly there** (`SetPosition`). This is precisely CLAUDE.md's "auto-drawn connector lines": the whole tree's visual layout is computed from a handful of per-connection direction/length/rotation values, not placed by hand.

```csharp
private void OnValidate()
{
    if (connectionDetails.Length != connections.Length) { Debug.LogError(...); return; }
    UpdateConnection();
}
```
`OnValidate` re-runs this layout math live in the **Editor**, outside Play mode, every time a connection detail is tweaked in the Inspector — so a designer sees nodes and connector lines update in real time while adjusting values, without pressing Play and without any custom Editor script at all. A genuinely nice example of how far `OnValidate` plus RectTransform math can get you toward an editor-like live-preview experience, entirely within ordinary runtime component code.

### `UI_ToolTip` — shared positioning, and the third off-map hide

```csharp
public virtual void ShowToolTip(bool show, RectTransform targetRect)
{
    if (!show) { rect.position = new Vector2(9999, 9999); gameObject.SetActive(false); return; }
    if (targetRect == null) return;
    gameObject.SetActive(true);
    UpdatePosition(targetRect);
}
```
The **third** confirmed occurrence of the off-map-hide trick (`Object_Portal` in `10-InteractiveObjects.md`; `UI_InGame.HideQuickItemOptions` in Part 6 above; now here) — solidly established as a recurring idiom in this codebase for "hide something without disabling logic that still needs to run" (here, `SetActive(false)` alone would have sufficed, but the position reset is a defensive habit layered on top).

```csharp
private void UpdatePosition(RectTransform targetRect)
{
    float screenCenterX = Screen.width / 2f;
    Vector2 targetPosition = targetRect.position;
    targetPosition.x = targetPosition.x > screenCenterX ? targetPosition.x - offset.x : targetPosition.x + offset.x;

    float halfHeight = rect.sizeDelta.y / 2f;
    if (targetPosition.y + halfHeight > Screen.height) targetPosition.y = Screen.height - halfHeight - offset.y;
    else if (targetPosition.y - halfHeight < 0) targetPosition.y = halfHeight + offset.y;

    rect.position = targetPosition;
}
```
Worth appreciating as real, solid UI engineering rather than a naive fixed-offset tooltip: it flips which **side** (left/right) the tooltip appears on based on whether the hovered target is left or right of screen center (so a tooltip near the right edge never tries to render off-screen to the right), and separately clamps the vertical position if the tooltip would extend above the top or below the bottom of the screen. Most of the simpler concrete subclasses below just call this once with different content.

### `UI_ItemToolTip`, `UI_StatToolTip`, `UI_SkillToolTip` — three concrete tooltips

- **`UI_ItemToolTip`** — shows buy/sell price (switching based on context flags passed from whichever slot triggered it), and a **rarity-tiered name color** (`GetColorByRarity`: white → green → blue → purple → orange as `itemRarity` increases) — the familiar loot-rarity color convention from many RPGs. This is what every `ShowToolTip(...)` overload called from `UI_ItemSlot`/`UI_MerchantSlot`/`UI_QuestRewardSlot` throughout this doc ultimately resolves to, with each caller's different boolean flags controlling which optional sections (merchant info, controls) actually display.
- **`UI_StatToolTip`** — a large `switch` of mostly hand-written, static explanatory text per `StatType`. One case is worth calling out specifically: `Armor` interpolates a **live** computed value directly into otherwise-static text (`playerStats.GetArmorMitigation(0) * 100`), showing the player's actual current mitigation percentage inline with the flavor explanation — a small but genuinely nice touch mixing static description with one number worth always showing fresh.
- **`UI_SkillToolTip`** — the richest of the three: name/description/cooldown, plus a dynamically built, **color-coded requirements list** (`GetRequirements`, using a `StringBuilder` — the same tool `Inventory_Item.GetItemInfo` uses, `07-InventorySystem.md`) marking each prerequisite green or red depending on whether it's actually met, and a separate "Locks out:" section listing conflict nodes. It also owns a **locked-node blink effect**:

## Where this pattern could be reused later

The **one base class + several thin `override`s reusing shared visual/update logic** shape (`UI_ItemSlot`'s seven descendants, `UI_ToolTip`'s three) is the standout, broadly reusable idea from this whole folder — worth reaching for in any UI system with many slot/tile/card-style elements that mostly look and update the same way but need different click behavior depending on context. The **direction/length/rotation-driven, `OnValidate`-live-updating layout engine** in the Skill Tree UI is a genuinely strong technique to remember for *any* future node-graph, tech-tree, or connected-diagram UI — it shows a real, substantial "editor-like" authoring experience is achievable through plain runtime components and `OnValidate`, without writing a single custom Editor script. And the **event-driven-replaces-polling** story told directly in `UI_MiniHealthBar`'s commented-out `Update()` is worth keeping as a concrete, first-person example of *why* to prefer reacting to a specific event over checking something unconditionally every frame — the kind of lesson that's easy to state abstractly but much more convincing seen as a real before/after in actual project code.
